## 2. 产品定位与边界

Council of Translation 是一个面向本地化翻译质量保障的 review-only MCP Server。调用方提供 Source、Target 以及可选的领域、受众、术语、风格、项目规则和技术约束；Council 从多个专业视角评估译文，保留分歧、盲区、证据和裁决过程。

项目关注的是“为什么可以接受、为什么需要修改、当前证据是否足够支持处置”，而不是尽快生成另一份翻译。

明确边界如下：

- `review_translation` 默认使用 `output_mode="review_only"`，不输出完整替换译文；显式 `with_snippets` 可返回局部建议，只有显式 `full_rewrite` 才允许完整建议译文。历史与诊断工具不生成译文。服务本身不修改调用方文件。
- 不负责翻译记忆库、术语库或风格指南的外部检索生命周期。
- 不负责把建议自动应用到目标文件。
- 不以多数票决定正确性。
- 不把 reviewer 的自信程度平均成质量分数。
- 不把法律风险审校角色包装成法律顾问，也不应编造法规或司法要求。
- 调用方或外层 agent 负责最终修改、发布和业务责任。

## 4. 核心术语

| 术语 | 本项目中的含义 |
| --- | --- |
| Finding | 单个 reviewer 返回的、经 schema 验证的轻量 MQM 风格注记；含锚点、类型、严重度、证据与建议动作。 |
| Reviewer envelope | reviewer 的双层输出：自然语言 `role_feedback` 与结构化 `findings`；损坏的 finding 会使该样本不可用。 |
| IssueCluster | 对指向同一有界问题的 findings 做相关性聚合后的议题；不是票数统计。 |
| Material Context Gap | 缺失后会实质改变结论、且调用方尚未回答的背景问题。 |
| Decision Point | 从有效、可定位的 `choice` finding 构造的有界用户选择；普通建议动作不能成为选项。 |
| Targeted Discussion | 对少量争议议题进行一次有界讨论；只有新的结构化锚点/来源或真实立场变化才计为新增价值。 |
| Position Matrix | 结合角色相关性、证据来源、约束层级与阻断状态的结构化立场矩阵；不采用简单多数票。 |
| Policy Gate | 在最终裁决前强制执行技术完整性、确定性硬约束、critical blocker 与有效选项边界。 |
| DNT | Do Not Translate，调用方要求逐字保留的内容。 |
| Coverage | 活跃 reviewer 中产生有效结构化样本的覆盖情况，与 finding 数量分开记录。 |
| Chief disposition | 主编最终处置：可发布、修改后可发布或需人工复核，并配套是否需人工复核。 |
| Decision support | 对“结构化证据是否足以支持当前主编处置”的确定性分类，不是译文正确概率。 |
| Truth table | 从覆盖、上下文、降级、fallback、实质分歧和处置一致性映射到 decision-support 等级的固定规则。 |
| Critical blocker | 不允许由用户偏好或多数意见覆盖的最高级实质风险；确定性 blocker 是其中可由本地规则直接验证的一类。 |

## 5. 当前执行流程

当前主流程可概括为：

```text
输入归一化与 Briefing
→ 确定性技术预检
→ 基于内容类型与模式生成 Council Plan
→ 有界并发的独立角色评审
→ Finding 验证与 Issue Clustering
→ 必要时提出 Material Context Gap
→ 必要时进行一次 Targeted Discussion
→ 必要时生成用户 Decision Point
→ 受影响角色定向复议
→ Policy Gate
→ Chief Editor Adjudication
→ 五节主报告与结构化记录
→ 持久化与 Verification Receipt
```

仅独立角色评审并发执行。Briefing、背景交互、讨论、用户决定、复议、Policy Gate、主编裁决、展示和持久化仍保持阶段顺序。

结构化 Finding 负责机器聚合与执行建议，角色自然反馈负责保留专业视角。只有经过验证的 `choice` 且带有有界 `proposed_value` 才能形成用户可选结果；普通 action 文案不能变成选项。用户只能在有效选项内行使决定权，不能覆盖技术完整性、确定性硬约束或 critical blocker。语义正确性主要来自 reviewer 的结构化模型证据和 Policy Gate 的保守裁决，并非像占位符 parity 那样可由本地代码普遍证明；这一区别应成为外部审计重点。

V0.13 的 `decision_support` 只回答“已验证的结构化证据对当前主编处置提供了何种程度的支持”，不回答“译文正确概率是多少”。等级为：

- `well_supported`
- `supported_with_limits`
- `insufficient`
- 旧记录兼容值 `not_recorded`

只有 `insufficient` 可以把意外宽松的处置收紧到人工复核；任何等级都不能放宽 Policy Gate、blocker 或用户权限边界。

八项继承指标的定义来自 `src/council_of_translation/evaluation.py`：critical issue recall、clean-case false-positive-free、role contribution-kind、conflict detection、user-authority behavior、chief consistency、call-budget adherence、discussion marginal-value。V0.13 另测 decision-support level accuracy、support/disposition coherence，以及 insufficient 分母内错误宽松处置的 false-reassurance rate。这里的 `1.0/0.0` 是 30 个确定性 Golden case 上的精确匹配率，不是生产准确率或统计置信区间。

精确计算规则如下；`N=30`，其中校准 case `C=6`：

| 指标 | 分子 / 分母 | 冻结目标 |
| --- | --- | --- |
| Critical issue recall | 在 fixture 期望 critical 的 case 中，运行结果出现 blocking 或 critical cluster 的数量 / 期望 critical case 数 | `1.0` |
| False-positive-free rate | `observed.false_positive_free == expected` 的 case 数 / `N`；clean case 要求零 cluster | `1.0` |
| Contribution-kind accuracy | 每个 case 的角色贡献分类 map 与 expected 完全相等的 case 数 / `N` | `1.0` |
| Conflict-detection accuracy | discussion 是否出现与 expected 相等的 case 数 / `N` | `1.0` |
| User-authority accuracy | 权限结果枚举与 expected 相等的 case 数 / `N` | `1.0` |
| Chief-consistency rate | 主编 rationale 存在且 blocker/critical 不被放宽的布尔值与 expected 相等的 case 数 / `N` | `1.0` |
| Call-budget accuracy | sampling_calls 精确匹配数加 sample_budget 精确匹配数 / `2N`，并额外禁止 calls 超预算 | `1.0` |
| Discussion marginal-value accuracy | 结构化讨论边际价值与 expected 相等的 case 数 / `N` | `1.0` |
| Decision-support accuracy | calibration case 的 level 精确匹配数 / `C` | `1.0` |
| Support/disposition coherence | calibration case 的 `outcome_coherent` 精确匹配数 / `C` | `1.0` |
| Insufficient false reassurance | 被观察为 `insufficient` 的 calibration case 中，未转人工复核或状态过宽松的数量 / observed-insufficient 数 | `0.0` |

所有 30 个 case 都参与九个基础 property 比较：`critical_issue_recalled`、`false_positive_free`、`contribution_kinds`、`conflict_detected`、`user_authority`、`chief_consistent`、`sampling_calls`、`sample_budget` 和 `discussion_marginal_value`。它们聚合成上表八项继承指标，因为 `sampling_calls` 与 `sample_budget` 两个 property 合并计算一项 call-budget accuracy。新增六个 `calibration_case=true` 还参与 `decision_support_level`、`publishability`、`review_needed`、`status` 和 `support_disposition_coherent` 五个校准 property 比较。case 输入、expected 值和类别映射固定在 `tests/fixtures/v24_golden_corpus.json`，聚合公式固定在 `src/council_of_translation/evaluation.py`，mutation controls 位于 `tests/integration/test_v24_golden_corpus.py`。

## 10. 主要安全与真实性不变量

- 默认 `review_only` 不输出完整建议译文。
- 占位符、DNT、required/forbidden literal、numeric/Markdown parity 可形成确定性 blocker。
- 模型声称的普通项目规则不会自动升级成确定性 blocker。
- 无效或部分损坏的 reviewer envelope 不得伪装成成功覆盖。
- 部分/零覆盖、未完成复议、未解决关键上下文和降级执行不能产生虚假正向信心。
- 同义或重复 finding 不增加 reviewer 权威，也不通过“多数票”决定结果。
- Verification Receipt 的生产 projector 被设计为不包含 Source、Target、reviewer/evidence prose、凭证、环境变量、文件路径或内部 issue ID；这一主张有内部 privacy/hostile tests，但仍属于待外部攻击性验证的安全性质。
- 历史缺失字段使用 `not_recorded` 或显式 unavailable，不以当前默认值回填历史事实。

## 12. 已知限制与剩余风险

以下事项尚未被本项目内部证据彻底消除，应由外部审计重点复核：

1. **模型依赖**：确定性框架可以约束流程和裁决边界，但不能保证 provider 对所有语言、领域和长文本稳定发现实质问题。
2. **语料代表性**：30-case Golden Corpus 是有界回归集，不足以代表所有语言对、行业、文体和真实生产分布。
3. **评价自洽风险**：测试、Golden fixture、聚合指标和实现由同一项目演进，需要外部检查是否存在过拟合或自证循环。
4. **真实成本与延迟**：Q-015 的服务墙钟约为 5.8～20.0 秒；不同 provider、网络、限流和账户条件仍可能显著变化。
5. **客户端差异**：Goose 当前可能只把结构化数据呈现在文本 fallback 中；其他 MCP Client 的双通道、elicitation 和 sampling 行为需要独立验证。
6. **长文本边界**：项目强调简洁报告和有界调用，但长文、多问题密度及跨段关联的召回率仍需要更大规模外部评测。
7. **治理边界**：GitHub `main` 强制六路 CI，但未要求人工 PR Approval；仓库也尚未创建 GitHub Release 或版本 Tag。
8. **非目标风险**：项目不管理外部术语库检索、翻译记忆、文件修改和发布，因此端到端产品质量仍依赖调用方正确提供上下文并正确应用建议。

## 13. 建议的外部审计问题

建议审计方至少回答以下问题：

1. 当前实现是否真正形成有条件的 deliberation/reconsideration，还是仍可被简化为并列采样加摘要？
2. 是否存在任何路径能绕过 Policy Gate、blocker、review-only 或用户有效选项边界？
3. `decision_support` 的 truth table 是否可能对错误的主编处置给出看似充分的支持？
4. Issue correlation、deduplication 和工作项投影是否可能错误合并不同缺陷，或把重复证据误计为新增价值？
5. Schema 2.6、receipt 1.1、历史兼容和 continuation 是否存在事实回填、字段漂移或处置不一致？
6. Canonical receipt 的文本和结构化通道是否真正来源于同一对象，且不存在隐私泄露路径？
7. 并发、预算和 wall-clock/sampling-wait 遥测是否准确，异常、取消、限流和 provider failure 是否安全降级？
8. Golden Corpus 与测试是否覆盖反例，而非只覆盖实现预期？是否需要盲测集或外部人工标注集？
9. 五节主报告是否在真实用户场景下足够简明、可行动，同时没有隐藏少数意见和关键限制？
10. 在规划任何新功能前，哪些技术债、安全问题或证据缺口应被列为阻断项？

## 14. 外部审计判定建议

建议把阶段审计结论限定为以下三种：

- **PASS**：未发现 high/critical 缺陷；固定提交可构建，核心不变量与负向反例可独立复现；证据链限制已明确记录。
- **PASS WITH FINDINGS**：没有可绕过 Policy Gate、泄露敏感内容、伪造覆盖/处置或破坏历史事实的阻断缺陷，但存在中低风险缺陷、证据缺口或改进项。
- **BLOCK NEXT CAMPAIGN**：发现可复现的权限/Policy Gate 绕过、确定性 blocker 失效、敏感信息泄露、记录与展示处置不一致、历史事实伪造、默认 review-only 破坏，或固定提交无法通过声明的核心测试。

模型在开放分布上的漏检、翻译偏好差异或单次 provider 波动，应按影响和可复现性分类，不自动视为架构 blocker；反之，“内部测试全绿”也不能否定外部发现。

建议严重度 rubric：

| 严重度 | 判定基准 | 阶段影响 |
| --- | --- | --- |
| Critical | 可导致不安全内容被错误放行、Policy Gate/权限边界绕过、敏感数据直接泄露、持久记录事实伪造或供应链不可控执行 | 必须 BLOCK |
| High | 核心路径系统性失效、重要处置或回执不一致、默认边界可被常规输入破坏，但尚无直接不可逆影响证据 | 原则上 BLOCK，除非审计方证明影响被可靠隔离 |
| Medium | 有界错误、重要证据缺口或兼容性问题；存在明确规避办法且不产生虚假发布许可 | PASS WITH FINDINGS |
| Low | 局部可用性、文档、性能或维护性问题，不改变安全/真实性处置 | PASS WITH FINDINGS 或记录建议 |

关键证据主张如果无法独立复核，则不得给出无条件 PASS：若缺失证据是该 Critical/High 主张的唯一支撑，应 BLOCK；若生产实现和负向测试可独立验证、缺少的只是历史运行原件（如 Q-015 原始会话导出），最多给出 PASS WITH FINDINGS，并明确该真实客户端主张未被第三方复证。

## 16. 审计交付建议

外部审计报告最好将结果分成三类：

1. **已证实缺陷**：附代码位置、可复现输入、期望与实际结果、严重度和影响范围。
2. **证据缺口或不确定性**：说明现有证据为什么不足，以及需要什么实验才能判断。
3. **产品或架构建议**：说明价值、代价和非目标，不与缺陷混为一谈。

每项发现建议包含：稳定编号、严重度、证据、可复现步骤、受影响不变量、是否阻断下一 Campaign、最小修复边界和建议验证方式。外部审计应先提交只读报告，不直接修改仓库或创建 PR；修复范围由后续 Foreman Campaign 单独冻结。
