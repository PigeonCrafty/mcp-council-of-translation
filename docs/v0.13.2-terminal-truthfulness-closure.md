# V0.13.2 Terminal Truthfulness Closure

## Confirmed defect

V0.13.1 correctly failed closed when a required Targeted Discussion envelope was malformed or unavailable. A later `continue_review` revision, however, could resolve an unrelated valid DecisionPoint and accidentally discard the parent's canonical `discussion_unavailable` evidence gap. That child could then report a permissive terminal state even though no new evidence had resolved the original cross-role disagreement.

## Bounded correction

V0.13.2 makes continuation finalization recognize only the exact canonical `discussion_unavailable` warning or an exact code in the parent's semicolon-delimited fallback list. Because continuation does not rerun Targeted Discussion, the child retains that unresolved gap, degradation, insufficient decision support, human-review status and chief disposition. The independent valid user choice remains effective: its selected outcome, affected-role reconsideration and `valid_user_choice` trace are preserved.

The correction does not inherit unrelated warnings or fallback codes and does not make clean continuations sticky. It adds no sampling, retry, elicitation or persistence operation.

## Schema and public boundary

No schema migration is required. ReviewRecord remains `2.6`, the verification receipt remains `1.1`, and the offline evaluator remains `2.1`. The public surface remains exactly five tools, the server remains review-only, sampling budgets remain `6/13/18`, and independent-review concurrency remains bounded at `3`.

## Verification scope

The local Campaign verification covers the adversarial parent/child path, a clean-parent negative control, immutable parent persistence, child linkage, sampling and save counts, full and compact records, phase trace, primary report, canonical receipt/text equality, affected regressions, the 30-case Golden corpus, complete regression, fresh archives and isolated installed-wheel smokes against the two supported FastMCP points.

This document records the intended local correction and verification plan. It does not claim Foreman acceptance, protected-main CI, publication, tagging, a GitHub Release, deployment or production-provider validation.

## Known support boundary and handoff

The correction is intentionally specific to the already-canonical Targeted Discussion gap. It does not introduce a general persistent-evidence-gap framework or claim that every future degradation class should be inherited. A structurally distinct sticky gap requires separate analysis and an explicit contract.

After independent acceptance and any separately authorized release work, the product should return to Feature Freeze and observation. Future changes should be driven by bounded evidence and a new Campaign rather than expanding this maintenance correction.
