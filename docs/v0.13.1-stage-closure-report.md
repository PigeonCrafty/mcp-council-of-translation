## 2. 产品定位

Council of Translation 是一个 review-only MCP Server，用于本地化翻译质量保障。调用方提交 Source、Candidate Translation 和可选的领域、受众、术语、风格、项目规则及技术约束；系统组织多个专业审校视角，形成结构化问题、分歧、盲区、处置建议和可验证回执。

产品不直接翻译文件、不管理翻译记忆库或术语库检索、不自动修改调用方资产，也不替代最终业务责任人。默认 `review_only` 模式不返回完整推荐译文；只有调用方显式选择允许完整改写的模式时，才可能生成 `suggested_translation`。

当前公共 MCP 工具恰好五个：

1. `review_translation`
2. `continue_review`
3. `view_review_record`
4. `list_review_records`
5. `get_server_info`

默认运行参数保持为 `review_only`、`interactive_mode=auto`、`briefing_mode=auto`、`trace_level=summary` 和 `history_mode=full`。lightweight、standard、strict 三档采样预算分别为 `6/13/18`；独立 reviewer 并发范围为 `1–3`，默认值为 `3`。

## 4. 当前已经实现的能力

### 4.1 有界 Council 编排

- 根据内容类型与审校模式选择冻结的 reviewer portfolio，目前覆盖 15 个路由 profile。
- 仅独立 reviewer sampling 并发；Briefing、背景补充、讨论、用户决定、复议、Policy Gate、裁决和持久化保持阶段顺序。
- 每个 reviewer 同时返回自然语言 `role_feedback` 和机器可聚合的 `findings`。
- 损坏或部分无效的 finding 列表按样本整体降级，不能伪装成成功覆盖。
- 重复或同义 finding 不增加 reviewer 权威，也不以简单多数票决定结果。

### 4.2 确定性完整性保护

- 支持占位符、printf token、URL、命令/flag、DNT 和显式 caller literal 的保留检查。
- 支持 `numeric_parity`、`markdown_parity`、`required_literal:<text>` 和 `forbidden_literal:<text>` 等调用方硬约束。
- 普通百分比文本和 URL 外部标点不会被错误提升为确定性 blocker。
- reviewer 的自然语言判断不能自行创建确定性规则或覆盖预检结果。
- 技术 blocker、critical blocker 和 Policy Gate 不能被用户偏好或 Council 多数意见放宽。

### 4.3 上下文、选择与复议

- Source/Candidate-only 请求可通过 Briefing 补充内容类型、用途、受众和重点。
- reviewer 可提出有限的 Material Context Gap；系统最多一次询问两个真正会改变判断的问题。
- 只有结构有效、具有具体 `proposed_value` 且能定位到单一锚点的 `choice` finding 才能形成 Decision Point。
- 用户对有效选项拥有决定权；违反硬约束、技术完整性或 critical blocker 的选项会先被移除。
- 只复议受用户选择或新背景实质影响的角色，并记录 requested/completed/skipped/failed provenance。

### 4.4 讨论、聚合与主编裁决

- IssueCluster 依据有界 source/candidate anchor、问题类型和修复目标进行保守关联。
- Targeted Discussion 是一次有界模型采样，用结构化输入模拟跨角色讨论；它不是多个 peer-to-peer agent 之间的通信。
- 无实质分歧时不制造讨论；损坏的讨论 envelope 原子降级，并完整保留讨论前证据。
- 讨论后的 consensus、minority report、value metrics 和 decision support 使用同一份最终立场事实。
- Chief Editor 通过 Policy Gate 和 Position Matrix 形成 `可发布`、`修改后可发布` 或 `需人工复核` 处置，而不是计票。

### 4.5 真实性与证据充分性

- `decision_support` 将当前处置分为 `well_supported`、`supported_with_limits` 或 `insufficient`；历史记录可为 `not_recorded`。
- 该字段只描述结构化证据对当前处置的支持程度，不是译文正确概率、质量分数或 reviewer confidence 平均值。
- 只有 `insufficient` 可以把意外宽松的结果收紧到人工复核；它不能放宽 blocker 或 Policy Gate。
- 部分/零 reviewer 覆盖、未解决关键上下文、未完成必要复议、运行降级和已知输入截断均 fail closed。

### 4.6 持久化、历史与客户端验证

- ReviewRecord Schema 2.6 保留完整结构化证据和阶段 provenance，并兼容 V1 及 V2.0–V2.5 读取。
- `view_review_record` 支持 `full`、`summary` 和 `verification` 三种视图。
- Verification receipt 1.1 由同一 canonical object 同时生成结构化内容和文本末尾的紧凑 JSON，适配忽略 structured content 的客户端。
- 历史缺失事实使用 `not_recorded`/unavailable 语义，不用当前默认值伪造历史。
- V1 summary 已最小化，只保留有界身份、模式、状态和终态信息。
- 回执 projector 默认不暴露 Source、Candidate、reviewer prose、evidence prose、凭证、环境变量、文件路径和内部 issue ID。

## 9. 当前边界与剩余风险

1. **开放分布模型质量**：框架能约束流程和处置，但不能保证 provider 对所有语言、领域、文体和隐含语境稳定发现问题。
2. **长文档能力**：单次 Source/Candidate 审校使用有界前缀；超过边界会诚实转人工复核。系统尚未实现文档分块、跨块关联或全文综合裁决。
3. **盲测代表性**：现有 30-case Golden Corpus 是确定性回归集；独立 blind set 已有 Schema，但大规模外部标注和统计评估仍属未来证据工作。
4. **Targeted Discussion 边界**：它是一轮有界模型讨论采样，不是多个独立自治 agent 的真实通信网络。
5. **客户端差异**：Goose、其他 MCP Client 对 structured content、sampling 和 elicitation 的呈现可能不同；文本 fallback 解决可读性，不保证所有客户端 UX 一致。
6. **端到端责任**：术语/TM 检索、文件修改、建议应用和最终发布由外层系统负责，Council 无法证明这些步骤被正确执行。
7. **供应链兼容**：FastMCP 2.13.0.2 会产生已知上游 Authlib deprecation warning；当前没有证据表明它构成 Council 产品缺陷。
8. **仓库治理**：六路 CI 和管理员保护已启用，但尚未要求人工 PR Approval，也没有正式 GitHub Release/Tag 流程。

## 11. 下一阶段建议

建议先进入短期稳定观察，而不是立即扩大功能面：

1. 收集真实用户对五节报告、工作项分组和人工复核触发频率的反馈。
2. 按 blind-set Schema 建立独立策展、与实现团队隔离的盲测语料。
3. 将 installed-wheel、双 FastMCP 和五工具 smoke 固化为可重复执行的仓库脚本。
4. 观察长文本 CLIENT_LIMIT、provider 波动、客户端 structured-content 差异是否形成重复问题。
5. 只有在出现清晰用户价值和可验证验收条件后，再冻结下一 Campaign。

下一 Campaign 的优先级建议依次为：外部盲测与证据工程、跨客户端兼容、可重复发布验证；长文档分块/跨块综合属于显著架构扩展，应单独评估，不宜作为小修补附带进入维护版本。
